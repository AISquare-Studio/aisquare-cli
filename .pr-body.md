## What & why

**A spawned agent is told the task it was spawned for.** Reported 2026-09-10 from the SOC 2 fleet: *"sometimes manager spawns the agent but does not assign task."*

**Symptom.** The manager runs `fleet spawn coder --label coder-x --task <id>` as its standing cycle says. The new coder comes up, reads the board, and either takes the *oldest* ready task instead of its own, or — when two coders are spawned together — both race for the same task while the intended ones sit idle. On the SOC 2 board the manager ended up posting `you are coder-rebase-soc2-prs. Run: aisquare task show tsk_… — then claim it…` notes by hand to make it work.

**Cause.** `fleet spawn --task` records the task on the `fleet_agent` row, names the label and branch after it, and sets `AISQUARE_FLEET_AGENT=<row id>` on the tmux window. Nothing read that variable. `hook_session_start` rendered the generic board plus the role's standing cycle, whose `task next --role coder --claim` is oldest-first by design.

**Change.**
- `core/orchestrator.py` — `env_fleet_agent()`.
- `services/team.py` — `_assignment()` at session start (and on the heartbeat's late-join path): reads the variable, joins the session to its row (fixes the "no board join for this agent" note for binaries whose session id could not be planned at spawn), and renders an **`ASSIGNED TO YOU: <id> [status] <title>`** block right under the identity line with the claim command. If someone already holds the task, it says so and tells the agent to ask the manager rather than take another. `next_task` tries the caller's assigned task first (same status/role/readiness rules), falling back to oldest-first — so parallel spawns stop racing, and a session with no fleet row behaves exactly as before.
- `core/harness.py` — the coder's standing cycle says assigned-first.
- `core/store.py` — `task_statuses` added to the `ContextStore` protocol (it existed on the implementation only).
