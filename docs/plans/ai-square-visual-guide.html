We are improving AI Square CLI’s existing team. You still talk to the manager. We give the team clearer instructions, more useful information, and recognisable voices that help you follow the work.

This page shows a proposed future experience. AI Square already has roles, worker sessions and a task board. The shared improvements and personality display described here have not been built. All jobs, messages and test results in the demonstration are illustrative.

What is a worker, a task ID, and “1 shell”?

A worker is a separate agent session doing a job. A task ID is the job’s reference number. A shell job is a command running inside an agent session—for example, checking whether a task has finished. “1 shell” does not mean one worker or a newly created account. Roles pass information through task records and messages, not by looking at screenshots of each other.

04 / What “personality” actually means

The facts stay fixed.
The voice changes.

A persona pack is a local file with character names and message patterns. One pack can contain a voice for every role. Studio and Mission Control are our two starter packs. A user can give one role a different pack.

Try the same failed check in three voices
UI tester: “The phone view cuts off the error message. This needs a fix.”
Official result · unchanged

Task T42 · tested build v1
Evidence: error text clipped at phone width.

Worker instructions · unchanged

Fix the clipped error message. Recheck the changed page on a phone-sized screen.

What the pack is allowed to change

The tone and wording of the activity displayed to you: calm, playful, concise, or another character you create.

What stays outside the pack

Task assignment, coding rules, tool permissions, required tests, saved errors, and the decision that something passed or failed.

The first release covers activity narration.

It appears next to the original manager/coder terminal and in the Board. It does not rewrite every original Claude reply. That would require another supported integration.

The first renderer uses saved message patterns, so displaying a persona adds no model calls. A separate AI can optionally help draft a pack once; live AI-written commentary is later work.

Where do I type /persona?

Inside AI Square’s own controls

Click Persona in Manager or a worker view, or press F12 → F1 → Personas. Type in the labelled AI Square command box.

/persona use mission-control

Set this project’s default voice.

/persona use calm-dev --role coder

Set a saved voice for coders in this project.

/persona off

Turn off project narration while work continues.

From a normal terminal
asq persona use mission-control

The same setting, through a shell command.

asq persona add ./calm-dev.json

Import a ready local pack. Preview it, then use it.

Proposed commands; they do not exist yet. A slash command typed directly into the current embedded Claude chat goes to Claude. Directly launched agent terminals do not automatically get an AI Square command box.

How a custom persona becomes a local file

You already have a pack
Choose JSON file / URL→Check file→Preview→Save locally→Select it

Imports do not activate themselves. Installed packs work offline. The file contains character data, not executable tools or agent instructions.

You have a character idea
/persona add --name calm-dev --text "Friendly senior developer. Brief updates and gentle humour."
Open editor→Edit starter phrases→Preview and save

Optional: ask a separate AI to draft the phrases once. The description stays out of working-agent conversations. Without that helper, edit the messages yourself; a description alone does not generate them.

What happens to my settings when new workers start?

A new coder inherits the project’s coder choice, or its default pack. Numbered coders keep their real names. Role choices override the project default. Project-wide Off hides all narration and preserves choices; changing a role while Off saves it without turning the project back on. Switching the project default preserves deliberate role choices. Settings survive restart.

05 / Where better work and lower usage could come from

Prepare once. Read what matters.
Check what was requested.

Personality makes the work easier to follow. The working improvements address mistakes and wasted effort. We must test whether they improve results and total usage; no percentage saving is promised.

Before work

A focused handoff

Give the coder the intended task, relevant requirements and useful code locations. Keep one shared job description instead of several drifting versions.

Example: “Connect the existing sign-in service to this page; make the error readable on a phone.”

During work

A useful short report

For supported commands, give the agent the result it needs to act. Keep original output for detail. Read relevant files after consulting the existing code map.

Example: “40 tests passed; browser layout was not checked by these tests.”

Before completion

Proof for each promise

Connect each requirement to evidence from the changed build. Keep missing checks visible. A new fix can require fresh tests.

Example: “Login passed, but the phone error is still clipped. This is unfinished.”

Both versions describe the same run. Failures and actionable warnings must survive. Unknown output stays ordinary. Asking for saved detail reads the original; it does not rerun the command. Initial support is limited to Git status and pytest. Automatic coverage across all tools is not promised.

The shorter report must reach the working agent. Making the screen look shorter alone does not reduce model input. Turning personality Off does not turn these working improvements off.

What does a developer actually connect?
  1. Persona settings and files

    One service imports, validates and selects packs. Shell commands and the AI Square command box call that service.

  2. A human-only display

    A shared renderer reads recorded events and picks the role’s wording. Manager, worker and Board views reuse it.

  3. The existing task and session system

    Add requirement links and load the right task/rules when each worker starts. Keep persona wording out of this path.

  4. The command-result path

    Run supported commands through a tested helper, save originals and send useful reports back to agents.

  5. Evidence and release checks

    Link checks to the requirement and tested build. Verify persona isolation, file imports, live switching and installed-package behaviour.

What remains outside the first release?

Rewriting every original Claude reply, continuous AI-generated commentary, individual-session persona overrides and full RTK-equivalent tool coverage. The first local personas do not need these. The wider work improvements also go beyond the original two-persona hackathon brief.

Does this guarantee better code or a smaller bill?

No result is assumed. Compare the same kinds of jobs with and without the working improvements. Measure correctness, requested outcomes, repeated attempts, time and actual model usage where available. Extra planning has a cost too. A smaller report is useful only if important information survives.

07 / How to explain it to someone else

“We are upgrading AI Square CLI’s team.”

You still open AI Square CLI, start the manager, and describe your job. We add clearer shared instructions so the team knows what success means, shorter useful reports so agents read less unnecessary information, and switchable personalities so you can follow who is doing what. The manager coordinates, workers build and check, and the final result is tied to evidence. Personality changes the words you see; the working improvements change how the team is prepared and checked.

What we should demonstrate: one real task, a visible worker handoff, a check that catches a problem, a correction, and an evidence-backed result. Switch personalities during that same work to show that only the display changes.
